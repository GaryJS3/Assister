# Google Calendar

Open **Calendars** in the dashboard (`/calendars.html`). Enable the Google Calendar API in your Google Cloud project, create a service account and download its JSON key. Share each existing calendar with the key's `client_email`. Use “Make changes to events” permission for writing; read-only shares support reading and announcements.

Connect the JSON file and give the account a name, then **Fetch calendars**. Sharing does not automatically put every calendar in the service account's calendar list. For missing calendars, copy the calendar ID from Google Calendar settings → Integrate calendar and use **Add shared calendar**. Select subscriptions and save. Multiple accounts are supported.

The long-lived credential is the service account private key, not a permanent access token. Assister signs a service account assertion and exchanges it at Google's fixed token endpoint; it caches short-lived access tokens and renews before expiration. Credential-provided token endpoints are never used. Domain-wide delegation and user OAuth sign-in are not implemented.

## Events

Choose a subscription and date range, then fetch events. Results are paginated. Create timed events in the browser's local zone or all-day events with an exclusive end date. Edit preserves fields outside the editor, including existing notification settings unless explicitly changed. Google etags prevent overwriting a concurrent edit. Editing/deleting an expanded recurring occurrence affects that instance; this page does not edit whole recurrence rules or guests.

Removal first fetches the event and prepares a five-minute single-use confirmation, then displays a confirmation dialog. Only **Confirm deletion** performs the Google DELETE with the fetched etag. There is no direct event DELETE endpoint. Assistant tools similarly prepare first and require a later explicit “confirm delete” message, scoped to the satellite and conversation. Restarting invalidates pending confirmations.

Assistant tools: `calendar_list`, `calendar_events`, `calendar_create`, `calendar_edit`, `calendar_delete`. Use requests such as “What's on my Google calendar tomorrow?”, “Add a dentist appointment to my family calendar tomorrow from 2 PM to 3 PM”, and “Move that event to 4 PM”. Clarify dates, calendars and titles when ambiguous. Tools use subscribed calendars only; create/edit require a current explicit mutation request. The dashboard also supports descriptions, locations, all-day dates, and disabling notifications.

## Announcements

For each subscription select any number of satellites and Rich API clients, enable **Send event notifications**, and configure **Assister notification schedule**. Add multiple advance rules such as 10 minutes, 2 hours, or 1 day before each event. Add daily agenda times such as 08:00 to list every event that overlaps that local day, including earlier events, recurring instances, and all-day events. Select the daily agenda time zone and save the subscription. These rules are stored by Assister and apply to every event, independently of all Google event and per-account reminder settings. A day before is 24 hours before the event start; all-day event starts use the Google calendar's time zone. Up to ten advance rules (maximum 365 days) and four daily agenda times are supported. Equivalent advance rules are deduplicated. Saving an empty schedule disables both advance notifications and daily agendas.

Existing subscriptions retain legacy Google reminder behavior until an Assister schedule is saved. The dashboard identifies this legacy state. Older API callers that omit `notifications` preserve the saved Assister schedule. The subscription input adds `notifications: { before: [{ amount: 10, unit: "minutes" }], dailyTimes: ["08:00"], timeZone: "America/New_York" }`. Google event reminder fields remain editable on events, but they do not control an Assister-owned schedule.

Each satellite has a separate delivery record. Busy, offline or failing satellites do not prevent Rich clients or other satellites from receiving their notification. Rich notifications use the existing authenticated `/api/client/notifications` and `notification.available` stream with kind `reminder`, importance `notify`, and an explicit target client. Rich client selection includes the configured owner; revoked or reassigned clients are skipped rather than routing calendar details to a new owner. Delivery to the notification store is durable acceptance, not proof of client display or playback. A client can retrieve the queued notification until the event starts (or for five minutes after an at-start notification). The existing client receipt endpoints remain available.

Google reminder preferences are per user: a calendar owner's personal notification settings are not necessarily the service account's settings. Sharing a calendar alone does not copy another user's notification preferences. Assister-owned schedules avoid this restriction entirely.

The poller runs every 30 seconds and looks ahead as far as the largest Assister advance rule (28 days for legacy Google reminders). It allows a five-minute grace period for delayed delivery and unavailable satellites. Advance notices skip events that have already started, except at-start notifications which retain the five-minute grace period. Daily agendas follow the selected time zone, adjust skipped DST times to the next valid minute, and run once at the later offset of a repeated time. The full agenda is fetched across all pages and snapshotted in SQLite for consistent retries after restarts. Cancelled events are excluded, empty days say “No events today,” and long agendas split into multiple notifications rather than dropping events. Rich agenda notifications remain available until five minutes after the local day ends; advance notices expire at event start (or five minutes after an at-start notice).

Successful delivery/queue acceptance keys persist in SQLite per calendar occurrence, rule and recipient. Rich client requests have deterministic idempotency keys and schedule fields to survive a crash between queuing and recording acceptance. Satellite delivery is at least once: a crash between playback and recording completion can repeat an announcement. Announcements use the existing satellite TTS/playback path. Later edits do not retract already queued Rich notifications or change a daily agenda snapshot prepared at its scheduled time. `/api/calendars/status` reports the most recent polling pass and sanitized failure; these are not physical playback verification.

## Storage and access

`google-calendars.json` under `Assister:DataPath` stores account metadata, subscription settings and encrypted credentials. Data Protection keys persist under `calendar-protection-keys` in the same directory. Preserve and protect both in backups; directory access grants the ability to decrypt credentials. Keys and credentials are never returned by account APIs. These management endpoints follow the existing trusted-network dashboard access model. This integration does not add internet-facing dashboard authentication.

Automated tests use generated RSA keys, fake Google responses and isolated SQLite/data directories. Deployment probes verify the running revision, dashboard assets, endpoints, and preserved configuration. Physical announcement playback and client display are separate acceptance checks; release validation does not trigger real announcements or edit Google events.

Each recipient section includes **All (current and future)**. These are persistent dynamic selections, resolved on every polling pass: all enabled registered satellites, and all active configured Rich API clients across owners. New recipients are included without saving the subscription again. Disabled satellites and revoked client credentials are excluded. Selecting All clears the corresponding explicit recipient list; turn All off to choose individual recipients again. Existing individual selections keep their previous behavior.
