## Findings and proposed fixes

### 1. Highest priority: one-time requests silently create recurring reminders

`d8b3bb8e` called `reminder_create` with hour 19, minute 54, weekday -1. The schema
defines -1 as daily. `161ce199` likewise created a daily 19:58 reminder. Neither
input requested recurrence. The latter response disclosed daily recurrence only
after creation; the former response did not disclose it.

The live reminder list confirms both remain active with next due times on October
27 at 19:54 and 19:58, respectively. IDs are
`a58e8ff8-d673-4621-83f0-469d2a84b6e5` and
`83a013d6-e4d7-4423-850e-d75e0e3a9791`. Advancing the due date does not establish
display, audible notification or acknowledgement on a client.

Cause: the reminder tool supports only daily/weekly schedules; creation requires
weekday, and its implementation accepts the model's -1 without verifying that the
user requested recurrence. A prompt saying one-time schedules are unsupported did
not enforce that restriction. Relative timing was also reduced to hour/minute.

Propose a persisted one-time due timestamp and explicit schedule kind, with
relative durations calculated in C# from a single request timestamp. Immediately
guard recurring creation in code: require explicit recurrence or clarification
before insertion. Never substitute daily recurrence for unsupported one-time intent.
Regression cases should include both exact inputs and assert schedule kind, due
instant and absence of unintended later occurrences. The two existing reminders
need user review; this audit leaves them unchanged.

### 2. Alarm wording and alarm importance fall through gaps between features

Both plain alarm requests omitted every reminder tool. `81206526` instead ran
`ha_search` for alarm, then said it could not set alarms and guessed 7:57 AM.
Adding the word reminder in `161ce199` enabled scheduling, but the creation schema
has no importance field. The scheduler's rich-client path publishes reminders as
`acknowledge`; this does not encode the requested `alarm` level.

Cause: `ReminderTool.Relevant` recognizes reminder/schedule/calendar words, not
alarm. Scheduling and notification importance are separate contracts with no
persisted linkage. This is an orchestration/schema gap, not simply model quality.

Propose recognizing time-qualified alarm requests through a shared scheduling
classifier, while keeping security alarm controls distinct. Add supported
importance to reminder persistence, tools and delivery, or explicitly clarify the
unsupported alarm behavior before creating anything. Require AM/PM when ambiguous.
Test plain alarm, alarm reminder, missing period and security alarm wordings.

### 3. Provider response failed validation; exact wire-level cause is missing

`541eb87c` failed in its first model round after 4.68 seconds with
`InvalidLanguageModelResponseException`, category `missing-or-invalid-finish-reason`.
No tool execution is recorded. Logs confirm the same exception category.

The provider client accepts only stop/tool_calls and categorizes length and
content_filter separately. The trace therefore supports an absent or unsupported
finish reason; it does not identify the actual value or prove token exhaustion.

Propose recording a bounded, redacted provider-protocol diagnostic: actual finish
reason, streaming mode, terminal-event presence and provider request ID. Fix the
producer/parser mismatch once that evidence exists. A single retry may be safe
when no mutation has been attempted; never replay an already attempted control.
Keep rejecting incomplete responses and never infer action success from them.

### 4. Fan command was accepted, but confirmation timed out

`29dc2226` matched the correct fan and speed deterministically. Container logs show
the POST to `fan/set_percentage` returned HTTP 200 in approximately 920 ms,
followed by 45 state GET requests, with successful HTTP responses, before
`TaskCanceledException` at approximately 10.04 seconds. Later `65ba8b65` retrieved
20% for the same fan. That later reading does not establish when it reached 20%.

Cause established: the command/readback operation exhausted its shared ten-second
budget without satisfying confirmation. Network rejection is not the explanation
supported by these logs. Exact mismatch is unknown because sampled power/speed
values and expected values were not recorded.

Propose distinct command-accepted and state-confirmed phases with bounded readback
telemetry, including observed speed, power and percentage step. Use a separate
confirmation budget appropriate to device reporting latency and retain an
accepted-but-unconfirmed receipt. Never automatically resend the command. Test
delayed state updates and mismatches before changing tolerances or timeout values.
The existing cautious response correctly avoided claiming completion.

### 5. Rich-client follow-up loses context after 30 seconds

`6d5cdeee` started 35.49 seconds after the fan response finished. Its conversation
ID changed and its model prompt contained only the new user question. The
coordinator deliberately expires context 30 seconds after response completion.
Playback acknowledgements may refresh that time; this trace does not show a
refresh that preserved this conversation. The later master-bedroom clarification
arrived within 14.73 seconds and retained its conversation successfully.

Propose separate rich-client chat lifetime from voice activation lifetime, or make
expiry visible and configurable. Retain device/owner isolation and never carry
action authorization forward. Record expiry reason and effective last-completion
time. Resolve a selected clarification candidate in C# to avoid two model rounds
for a simple read-only follow-up. The model's request for clarification was
reasonable given its empty history; the generic wording was unnecessarily broad.

### 6. Voice activation ended before audio delivery

`d19d11ac`, satellite `echomuse-G090LF1182030WPN`, reports zero PCM bytes and
`no_speech_timeout`. Controller logs for the exact transport session
`05c17b83-ec96-4978-84f9-737e123cd1bb` show controller wake detection at score
0.998, arbitration win, activation sound playback, then no-speech timeout. They
also record a device wake-detector miss and a defensive mic_start after the turn.

Cause remains unresolved: accidental wake, silence/energy gating and microphone
handoff/delivery cannot be distinguished here. Zero bytes at Assister do not prove
the device microphone produced no samples. This is not evidence of STT
misrecognition or semantic endpointing failure; endpointing made zero model calls.

Propose per-session counters at device reception, controller speech gate,
forwarding and Assister receipt, plus microphone ownership/start acknowledgements
around activation-sound playback. Verify a deliberate physical activation before
adjusting thresholds or blaming the STT provider.

### 7. Capability explanation mixed notification behaviors

`86399c9b` ran no tools and incorrectly attached ten-minute acknowledgement repeats
to high-importance. At deployed revision, `SatelliteAnnouncementTool` distinguishes
high-importance (beeps plus one repeat), acknowledge (ten-minute repeat), alarm
(ten-second repeat), and explicitly says rich-client importance is advisory.
The answer omitted that rich-client qualification. Local uncommitted edits alter
this description, so the deployed definition is the relevant comparison.

Propose a structured, read-only capability description generated from the same
delivery policies and client capabilities used at runtime. Render exact level and
transport semantics instead of relying on free-form paraphrase of tool prose.
